# 보안 점검(읽기 전용 감사)

사용자가 고른 자기 코드 폴더를 읽기만 해서 취약점 후보를 찾고, 찾은 후보를 스스로 반박해 본 뒤 남은 것만 근거와 함께 보고한다. 이 점검은 앱 전체가 안전하다는 증명이 아니다.

## 언제 쓰나

- 내가 만든 앱·서비스 코드의 보안 점검, 배포 전 보안 검토, 특정 기능(로그인·결제·파일 업로드)의 취약점 확인.
- 쓰지 않는 경우: 남의 서비스·운영 서버 공격 시험, 비밀번호 추측, 코드 수정(mody-dev-crew로 따로 요청).

## 실행 환경

- 실행기가 대상 폴더를 읽기 전용으로 연다. 파일을 만들거나 고치거나 지우지 않는다.
- 명령 실행 도구가 있어도 대상 코드·테스트·빌드를 실행하지 않는다. 읽기·검색만 한다. 실행해야 확인되는 것은 needs_validation 으로 남긴다.
- 네트워크로 무엇을 받거나 보내지 않는다. 의존성을 설치하지 않는다.
- 보고 파일은 실행기가 마지막 응답의 JSON으로 만든다. 마지막 응답 끝에 아래 형식의 ```json 블록 하나를 넣는다.

## 먼저 확인할 것

1. 요청 원문에서 점검 대상·범위·제외 범위를 읽는다. 범위가 없으면 대상 폴더 전체를 범위로 한다.
2. 대상이 사용자 자신의 코드인지. 다른 회사 서비스 공격이나 운영 서버 시험을 요구하면 점검하지 않고 이유를 적는다.
3. 저장소 지침(README, SECURITY.md, AGENTS.md)과 구조(진입점, 라우팅, 인증, 저장소, 외부 연결).

## 절차

1. **정찰**
   - 진입점, 사용자 입력이 들어오는 곳, 인증·권한 검사, 비밀값 보관, 외부 연결, 파일·명령 실행 지점을 정리한다.
   - 검사할 범위를 영역별 목록으로 만든다. 다 보지 못한 영역은 끝까지 '검사하지 못한 범위'에 남긴다.
2. **후보 발견**
   - 영역마다 입력 검증 누락, 인증·권한 우회, 주입(SQL·명령·경로), 비밀값 노출, 안전하지 않은 설정, 의존성 위험, 데이터 노출을 찾는다.
   - 후보마다 진입점부터 위험 지점까지 이어지는 근거(파일·줄)를 적는다.
3. **반박 검증**
   - 후보를 찾은 관점과 반대로, 이미 막아 주는 검증·미들웨어·설정·프레임워크 기본값이 있는지 찾아 반박을 시도한다.
   - 다른 방어층이 막아 주면 취약점이 아니라 강화 메모로 옮긴다.
4. **판정**
   - confirmed: 진입점부터 위험 지점까지 근거가 끊기지 않고, 재현 조건을 말할 수 있다. 심각도(critical·high·medium·low·informational)와 확신도를 붙인다.
   - needs_validation: 실행·환경·설정 확인이 있어야 결론이 난다. 심각도를 붙이지 않고 막는 요인과 검증 계획을 적는다.
   - rejected: 반박됐다. 반박 근거를 적는다.
5. **범위 기록**
   - 검사한 범위와 검사하지 못한 범위(이유 포함)를 나눠 적는다.
6. **보고**
   - 한국어 요약 뒤에 JSON 블록을 붙인다. 비밀값은 위치만 적고 값은 옮기지 않는다.

## 결과물 형식

마지막 응답 끝의 JSON(이 형식 그대로, 경로는 대상 폴더 기준 상대 경로):

```json
{"scope":{"target":"폴더 이름","checked":["검사한 범위"],"notChecked":["검사하지 못한 범위와 이유"]},"architecture":"구조·신뢰 경계 요약","findings":[{"id":"F1","title":"제목","status":"confirmed","severity":"high","confidence":"medium","evidence":[{"file":"src/api/login.ts","line":42}],"trace":"진입점에서 위험 지점까지","reproduction":"재현 조건","impact":"영향","verification":"검증 방법","recommendation":"권장 수정","limits":"검증 한계"},{"id":"F2","title":"제목","status":"needs_validation","evidence":[{"file":"server.js","line":10}],"blockers":"결론을 막는 요인","verification":"검증 계획","limits":"검증 한계"},{"id":"F3","title":"제목","status":"rejected","evidence":[{"file":"lib/db.js","line":5}],"rejectionReason":"반박 근거"}],"hardening":["강화 메모"]}
```

- confirmed 는 severity·evidence·reproduction·impact·verification·recommendation 이 모두 있어야 한다. 하나라도 없으면 실행기가 needs_validation 으로 낮춘다.
- 실행기는 evidence 의 파일과 줄이 대상 폴더에 실제로 있는지 확인한다. 없는 근거만 있는 confirmed 도 needs_validation 으로 낮춘다.
- 확인된 항목이 0건이어도 정상 결과다. 억지로 만들지 않는다.

## 승인·안전 기준

- 대상 코드를 실행하지 않는다. 대상 폴더를 고치지 않는다. 운영 서비스·남의 시스템을 시험하지 않는다.
- 외부 업로드, 유료 API 호출, 의존성 설치를 하지 않는다.
- 비밀값·토큰·개인정보 원문을 응답에 쓰지 않는다. '비밀값 있음(파일·줄)'로만 적는다.
- 이 점검 하나로 앱 전체가 안전하다거나 모든 취약점이 없다고 말하지 않는다. 한 번의 점검은 일부만 찾을 수 있다.

## 하지 않는 것

- 취약점 수정(별도 개발 요청으로 넘긴다), 공격 코드 작성, 보호 장치 우회 방법 안내.
- 근거 파일·줄 없이 confirmed 판정하기, 검사하지 않은 범위를 검사했다고 적기.
