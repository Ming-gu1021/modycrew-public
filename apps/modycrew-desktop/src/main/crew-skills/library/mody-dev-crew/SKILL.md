# 개발팀 기본 절차

작업 크기를 먼저 정하고, 작은 수정은 가볍게, 큰 변경은 설계 확인 뒤에 구현한다. 테스트로 먼저 실패를 확인하고, 다시 돌린 검사 결과로만 완료를 말한다.

## 언제 쓰나

- 기능 추가, 버그 수정, 리팩터링, 테스트 작성, 코드 리뷰, 코드베이스 파악.
- 쓰지 않는 경우: 배포·스토어 제출·서버 설정 변경(승인 필요 작업), 화면 시안만 필요한 일(mody-design-crew), 보안 점검(mody-security-audit).

## 실행 환경

- 현재 폴더가 작업 폴더다. 요청 원문은 `REQUEST.md`에 있다.
- 사용자가 폴더를 지정했다면 `TARGET.md`에 경로와 권한(읽기 또는 수정)이 있다. 읽기 권한이면 그 폴더의 파일을 바꾸지 않는다.
- `PHASE.md`가 있으면 그 단계만 한다. '계획 단계'면 대상 폴더를 고치지 않고 `output/plan.json`·`output/plan.md`만 만든 뒤 멈춘다. '구현 단계'면 `APPROVED-PLAN.md`의 계획대로 구현한다.
- 결과 파일은 `output/` 아래에만 만든다. 수정 권한을 받은 대상 폴더만 예외다.
- 함께 쓰라고 지정된 설치 스킬이 `.claude/skills` 또는 `.agents/skills` 아래에 있으면 그 SKILL.md를 먼저 읽는다. LOCAL_REVIEW_NOTES.md가 있으면 함께 읽는다.
- 패키지 설치, 원격 API 호출처럼 네트워크가 필요한 단계는 실행하지 않고 필요 항목으로 적는다.
- 외부 게시·배포·발송·결제·삭제·대량 다운로드는 하지 않고 승인 필요로 남긴다.
- 마지막 응답은 한국어로 쓴다: 한 줄 결론, 만든·바꾼 파일 목록, 실제로 확인한 것과 확인하지 못한 것, 사용자 승인 필요 항목.

## 먼저 확인할 것

1. `REQUEST.md`의 요청 유형: 기능·버그·리팩터링·테스트·리뷰·파악 중 무엇인가.
2. `TARGET.md`의 경로와 권한, `PHASE.md`의 단계.
3. 저장소 지침: AGENTS.md, CLAUDE.md, README, CONTRIBUTING. 이 문서와 다르면 저장소 지침을 따르되 승인·안전 기준은 더 엄격한 쪽을 따른다.
4. 작업 전 상태: `git status --short` 결과를 기록해 사용자가 이미 바꿔 둔 파일을 구분한다.
5. 검사 명령: package.json scripts, Makefile, pyproject.toml 등. 의존성이 없으면 설치하지 않고 미실행 사유로 적는다.

## 절차

단계마다 괄호 안 동반 스킬이 설치돼 있으면 그 SKILL.md를 먼저 읽고 적용한다.

1. **작업 크기 판정·계획**
   - 바꿀 파일이 3개 이하이고 공개 API·데이터 구조·인증·결제를 바꾸지 않으면 작은 수정, 아니면 큰 변경이다.
   - 큰 변경은 구현 방식 2~3안을 장단점과 함께 쓰고 추천안을 고른다. 사용자 확인 전에는 코드를 고치지 않는다.
   - 계획은 바꿀 파일 경로와 확인 방법이 붙은 작은 단계로 나눈다. 빈 단계(나중에 정함)를 두지 않는다.
   - 산출물: `output/plan.json`(아래 형식), `output/plan.md`
2. **요구사항·인수 조건**(agile-product-owner)
   - 사용자 이야기 1~3개와 인수 조건 3~7개를 '상황/행동/결과'로 쓴다. 모호한 점은 가정으로 표시한다.
3. **기존 코드 이해와 재사용**(codebase-onboarding)
   - 진입점, 관련 파일(최대 10개), 데이터 흐름, 테스트 위치와 명령을 15줄 이내로 요약한다.
   - 새로 만들기 전에 차례로 확인한다: 꼭 필요한가 → 저장소에 이미 있는가 → 표준 라이브러리·플랫폼 기능 → 이미 설치된 의존성 → 최소 코드. 처음 맞는 칸에서 멈추고, 몇 줄 때문에 새 의존성을 넣지 않는다.
4. **설계·분담**(senior-architect)
   - 바꿀 파일·함수와 이유, 기각한 대안, 위험, 화면·로직·데이터·테스트 분담을 적는다.
5. **테스트 먼저**(senior-qa)
   - 바꿀 동작의 테스트를 먼저 쓰고 실패를 확인한다. 버그는 재현 테스트부터 쓴다. 분기·파서·돈·보안 로직에는 작은 테스트나 검증을 남긴다.
6. **코드 수정**(화면은 senior-frontend)
   - 테스트를 통과시키는 최소 변경만 한다. 요청받지 않은 추상화·옵션·'나중을 위한' 코드는 넣지 않는다.
   - 입력 검증, 오류 처리, 보안, 접근성, 데이터 손실 방지, 테스트는 줄 수를 줄이려고 빼지 않는다.
   - 사용자가 이미 바꾼 줄은 건드리지 않는다. 같은 줄을 고쳐야 하면 멈추고 보고한다. 비밀값은 환경 변수 이름만 쓴다.
   - 읽기 권한이면 `output/proposed.diff`(unified diff)만 만든다.
7. **변경 검토**(pr-review-expert)
   - `git diff`를 처음부터 다시 읽고 정확성 → 안전 → 테스트 → 성능 → 군더더기 순으로 본다. 구체적인 실패 사례가 없는 지적은 하지 않는다.
   - 고칠 것은 반드시·권장·선택으로 나누고, 반드시 항목은 이번에 고친다.
8. **완료 전 재검증**
   - 검사 명령을 처음부터 다시 돌려 출력과 종료 코드를 확인한 뒤에만 통과라고 쓴다. 로그인·실기기·네트워크가 필요한 확인은 '미확인'이다.
9. **보고**
   - `output/dev-report.md`를 완성하고 마지막 응답을 쓴다.

## 결과물 형식

`output/plan.json`은 이 형식 하나만 쓴다(실행기가 읽는다).

```json
{"size":"small","files":["src/a.ts"],"publicApiChange":false,"dataModelChange":false,"authOrPaymentChange":false,"summary":"한 줄 요약","options":[{"name":"안 A","pros":"장점","cons":"단점"}],"recommendation":"안 A","checks":["npm test"]}
```

`output/dev-report.md`는 아래 제목을 이 순서로 쓴다.

1. 작업 크기 판정과 계획 — 작은 수정/큰 변경, 이유, 승인된 계획과 달라진 점
2. 요구사항·인수 조건 — `| 번호 | 인수 조건(상황/행동/결과) | 충족 | 근거 |`
3. 코드 이해 요약 — 15줄 이내, 재사용한 기존 기능
4. 설계 — 바꿀 곳, 대안과 기각 이유, 분담
5. 변경 파일 — `| 파일 | 변경 내용 | 추가/삭제 줄 | 이유 |`
6. 실행한 검사와 결과 — `| 검사 | 명령 | 결과(통과·실패·미실행) | 종료 코드 |`, 먼저 실패를 확인한 테스트 표시
7. 남은 실패·위험 — `| 항목 | 영향 | 다음 조치 | 승인 필요 |`, 생략한 것과 그 위험 1~2줄
8. 되돌리는 방법 — 작업 전 깨끗했던 파일은 `git restore -- <파일>`, 새 파일은 삭제 대상 목록, 이미 변경이 있던 파일은 이번에 바꾼 줄 범위

## 승인·안전 기준

- 코드는 `TARGET.md`에서 수정 권한을 받은 폴더 안에서만, 큰 변경은 설계 확인 뒤에만 고친다.
- 배포, 푸시, 파일·브랜치 삭제, `reset --hard`·`clean` 같은 강제 되돌리기, 의존성 설치·추가·업데이트는 실행하지 않고 승인 필요로 남긴다.
- 커밋은 `REQUEST.md`에 요청이 있을 때만 한다. `.env`·키 파일의 값은 어디에도 쓰지 않는다.
- 테스트가 실패한 상태를 완료라고 보고하지 않는다. 운영 데이터 변경, 결제·외부 API 실제 호출을 하지 않는다.

## 하지 않는 것

- 사용자의 기존 변경을 되돌리거나 덮어쓰기.
- 테스트를 통과시키려고 테스트를 지우거나 건너뛰게 바꾸기, 실행하지 않은 검사를 통과로 적기.
- 요구와 관계없는 대규모 리팩터링·포맷 변경.
